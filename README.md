# freeweb-resolver

Локальный резолвер, который позволяет обычному браузеру (Safari, Chrome — без
расширений) открывать децентрализованные домены `.eth` (ENS + IPFS) так же,
как обычные сайты — с валидным замком в адресной строке.

Прототип. Не production-хардненный код, обкатан только вручную, тестов нет.
Используется на свой страх и риск.

## Как это работает

```
браузер → локальный DNS (перехватывает .eth/.test) → 127.0.0.1
        → локальный HTTPS-шлюз (сертификат от локального CA)
        → резолвинг ENS-имени в Ethereum (JSON-RPC)
        → contenthash → запрос к локальной IPFS-ноде (kubo)
        → настоящий контент сайта отдаётся браузеру
```

Три отдельных фоновых процесса:
1. `resolver` (этот репозиторий) — DNS-резолвер + HTTPS-шлюз.
2. `ipfs daemon` (kubo, ставится отдельно) — забирает контент из сети IPFS.
3. Публичный RPC-эндпоинт Ethereum (по умолчанию `ethereum-rpc.publicnode.com`,
   настраивается флагом) — единственная оставшаяся точка доверия третьей
   стороне, замена на свою ноду не сделана.

## Модель доверия — прочитать перед установкой

Установка создаёт **собственный корневой сертификат (CA)** и добавляет его в
доверенные в системной Связке ключей. Это значит, что операционная система
будет считать сертификаты, подписанные этим CA, легитимными — ровно как
сертификаты настоящих публичных удостоверяющих центров.

Важно: сервер **не** подписывает сертификат на произвольный домен — только на
зоны из списка `--zones` (по умолчанию `test.,eth.`). Проверка на это есть
и в DNS-слое, и отдельно в TLS-слое (после исправления реальной уязвимости,
найденной ревью безопасности: изначально TLS-слой подписывал что угодно —
подробности в истории коммитов). Если ты меняешь код — не убирай эту
проверку в `cert.go` без крайней необходимости, иначе любой локальный
процесс сможет получить доверенный сертификат на произвольный сайт.

## Установка

```sh
./install.sh
```

Соберёт бинарник и напечатает оставшиеся шаги (они требуют пароля и
интерактивного терминала, поэтому не автоматизированы). Либо руками:

```sh
go build -o resolver .
```

Отдельно поставить и запустить `kubo` (IPFS-ноду):
```sh
# скачать с https://dist.ipfs.tech/kubo — актуальную версию под свою платформу
ipfs init
ipfs daemon
```

Запустить резолвер (тестовые порты, ничего в системе не трогает):
```sh
./resolver
```

Добавить CA в доверенные (введёт пароль — команда требует интерактивного
терминала, из скрипта не сработает):
```sh
security add-trusted-cert -r trustRoot -k ~/Library/Keychains/login.keychain-db ca/ca.crt
```

Проверить, что всё работает, не трогая системный DNS:
```sh
curl --resolve vitalik.eth:15443:127.0.0.1 https://vitalik.eth:15443/
```

Чтобы `.eth`-имена резолвились сами, без `--resolve` в каждой команде,
**не переключай системный DNS целиком** — это конфликтует с VPN, если он
у тебя включён (VPN-туннель на macOS обычно и так владеет системным DNS).
Вместо этого используй встроенный в macOS механизм split-DNS — он работает
только для перечисленных зон и не трогает всё остальное, включая VPN:

```sh
sudo mkdir -p /etc/resolver
sudo sh -c 'printf "nameserver 127.0.0.1\nport 15353\n" > /etc/resolver/eth'
sudo sh -c 'printf "nameserver 127.0.0.1\nport 15353\n" > /etc/resolver/test'
```

После этого `vitalik.eth` резолвится в `127.0.0.1` через обычный системный
резолвер (проверить: `dscacheutil -q host -a name vitalik.eth`), а весь
остальной трафик, включая VPN, работает как раньше — эти два пути вообще
не пересекаются.

Сайт при этом открывается по адресу с портом, например
`https://vitalik.eth:15443/` — сам HTTPS-шлюз слушает `15443`, а не
привилегированный `443` (его слушать может только процесс с правами root,
это отдельный шаг для полноценного деплоя через `launchd`).

## Удаление

```sh
security remove-trusted-cert -d ca/ca.crt   # убрать CA из доверенных
rm -rf ca/                                   # удалить сам CA и приватный ключ
sudo rm -f /etc/resolver/eth /etc/resolver/test   # убрать split-DNS зоны
```

## Флаги

Полный список: `./resolver -help`. Основные: `-zones`, `-eth-rpc`,
`-ipfs-gateway`, `-dns-listen`, `-http-listen`, `-https-listen`.

## Известные ограничения

- Изменяемые ссылки (`/ipns/...`) резолвятся не всегда — зависит от
  доступности записи в P2P-сети (DHT), это ограничение самого IPFS, не баг
  этого инструмента.
- RPC на Ethereum — единственная оставшаяся точка доверия третьей стороне.
- Нет установщика/анинсталлера — шаги выше делаются руками.
- Handshake (`.hns`) пока не реализован, только ENS (`.eth`).
